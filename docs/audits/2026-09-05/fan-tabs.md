## Threat model and current trust boundaries

The five actual visible tabs are Feed, Highlights, Create, Discover, Profile (`app/(tabs)/_layout.tsx:130`). Messages/notifications are header destinations; map, game/event, team/program, follow lists, and settings are nested routes. Fan taps call typed API clients; JWT+database auth identifies the viewer; Prisma membership/follow/privacy and approval state must control every content response. Public OG crawlers are a separate unauthenticated entry point. Media-host validation proves hosting origin, **not** viewer authorization. Stories use a different table/query from posts, creating a concrete sibling-path privacy gap.

Primary threats checked: URL-ID substitution into private fixture/read routes; private/blocked author leakage through stories and share previews; scoped-query widening after blocks; adult/minor and missing-DOB DM bypass; fabricated conversation IDs; profile/follow cache invalidation; deep-link allowlists; past-map-date bypass of post-access constraints. No payment/provider claims are made here.

## Confirmed open bugs

### FAN-01 — Private-team fixtures remain readable anonymously through direct IDs (High)

- Source: `server/src/routes/games.ts:978` (`canViewGameRecord`, public-approval early return at986), `games.ts:169` (`canViewGameMedia`, same early return189), `games.ts:2317` direct route, `games.ts:2357` summary; `server/src/routes/events.ts:1133` direct route, approval-only gate1166; `server/src/routes/og.ts:139`/194.
- Real PostgreSQL + actual production Express application HTTP reproduction: create active private team, approved linked game and standalone team event, unrelated verified fan. `/games?limit=100` and `/events?limit=100` correctly hide both fixtures. Direct `/games/:id` and `/events/:id` return200 to that fan **and to an anonymous request**. `/games/:id/summary` returns200 including secret title. `/games/:id/stories` returns the private game's media anonymously. `/og/games/:id` and `/og/events/:id` disclose secret title/location.
- Expected: unknown viewers receive404 or generic public share page consistently with list filters. Actual: knowing a previously shared fixture ID bypasses the private-team boundary.
- Exploitability × blast radius × recoverability: unauthenticated known-ID request; all approved fixtures of private teams across these routes; response disclosure cannot be recalled and public previews cache for300 seconds. This is not a coach write-authority bypass.
- Fix strategy: one shared viewer-aware entity visibility policy combining approval/opponent consent AND team privacy across by-id, summary, media, voting/RSVP, and OG/share siblings; retain the documented contributor permanent-view exception deliberately. Add tests for private home/away/direct-event/game-backed-event and authorized member/follower/owner positive controls.

### FAN-02 — New OG image fallback exposes private-profile media (High; regression introduced September4)

- Source: `server/src/routes/og.ts:34` selects best undeleted media post by game/event, with no author-privacy or private-team condition; used at142/197. `firstAllowedImageUrl`27 only checks allowed host. Introduced in `5e81d498`.
- Real reproduction: a private-profile author posts media on a public game and on a public event, neither has a banner. Unrelated fan GET `/posts/:id` returns404 for each. Anonymous GET corresponding `/og/games/:id` and `/og/events/:id` returns200 with the exact private image URL in `og:image`; response is `Cache-Control: public, max-age=300`.
- Expected: select a post visible to an anonymous viewer or branded fallback. Actual: private-profile image published through share preview despite normal post endpoint denying access.
- Exploitability × blast radius × recoverability: anonymous crawler/direct HTTP access, public event/game lacking its own banner, highest-ranked hidden-author media; cache/share propagation makes full recall difficult.
- Fix strategy: apply shared anonymous post visibility filters to fallback query before ranking, then hosted-media validation; both game and event branches need regression cases. Also evaluate whether video-without-poster should fall back to branded image.

### FAN-03 — Stories omit private-author and block filters (High)

- Source: `server/src/routes/games.ts:282` queries story rows by `game_id` only; same `makeListMediaHandler` mounted at2783 (`/media`) and2830 (`/stories`). Legacy SQL fallback318 also filters only game ID.
- Real reproduction: seed a current, unexpired story on a public game authored by a private-profile user. A stranger and anonymous viewer both get200 containing the story. Add viewer→author block; viewer still receives the story. Normal post privacy control in FAN-02 returns404.
- Expected: private-profile access and bidirectional block filtering apply before take50 and before serialization, with consistent legacy behavior. Actual: story media, caption, and user_id bypass post privacy.
- Exploitability × blast radius × recoverability: unauthenticated private stories and signed-in blocked stories on known public games; all matching story rows in newest50; downloaded media is not recoverable.
- Fix strategy: shared story visibility clause plus game/team gate, applied before pagination to both query paths; test private, accepted-follow, blocked-in-both-directions, and anonymous personas. Story expiry filtering also deserves a separate race test because cleanup is launched asynchronously while reads have no expires_at predicate; not claimed as reproduced here.

### FAN-04 — Profile post-loading failure is presented as an empty account (Medium)

- Component reproduction: actual ProfileScreen in React Native test renderer, stable signed-in fan, real react-query observer (no retries), mocked `User.postsForProfile` rejecting with network failure. Screen renders “No posts yet” and no post-loading error. This is a mocked-network component test, not device E2E.
- Audit observation test: `app/__tests__/audit-profile-failure-20260905.test.tsx`; one passing observation test explicitly asserts current broken output, not acceptance of desired behavior. Log `fan-profile-failure.log`. Initial attempts hit mock-shape/stable-hook harness problems; final test passes.
- Expected: actionable active-tab error with retry on first-page failure; retain cached items on background failure and distinguish failed pagination. Fix can be small and should cover all three sibling tab queries. Client delivery requires OTA after fix.
