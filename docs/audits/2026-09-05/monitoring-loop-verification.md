## Proposed loop — concrete next implementation

1. **Repair intake and monitor failures first.** Persist feedback in the existing support-report path, including message/category and an access-controlled screenshot reference. Return a report ID only after storage succeeds. Reuse the existing BullMQ/email provider mechanism for retryable notification. Add tests for failed storage, failed notification, duplicate submission, founder-only access, and reporter isolation. Fix the uptime alert condition using an explicit failure/status predicate and test its failing-check branch locally.
2. **Identify the exact running version.** Attach server commit, client OTA update ID, runtime/build, platform, environment, screen/route, and a request/correlation ID. Add these to Sentry and PostHog using their existing initialization paths. Do not attach email, tokens, or feedback content to analytics. Record server, OTA and web deployment identities separately in a release manifest; run security checks against the deployed commit in addition to PR/default-branch checks.
3. **One incident queue.** Connect Sentry production issues, failed monitoring/scanning jobs, and confirmed support bugs to one GitHub issue per stable fingerprint. Include sanitized evidence, affected release, first/last occurrence, affected-user count, owner, severity, and reproduction status. Updating an existing incident prevents repeated alerts from creating duplicate work. Sentry owns technical error incidents; PostHog provides user-journey impact and conversion anomalies, avoiding duplicate error pages from both.
4. **Respond in minutes; fix through verified PRs.** Proposed targets: critical payment settlement/refund, privilege-boundary failures, startup crashes, and sustained outages notify the designated owner immediately; acknowledge within 10 minutes. New ordinary errors get a daily triage queue. An automation can collect evidence, reproduce in isolated fixtures, add a failing regression, prepare a fix and draft PR. Unreproduced bugs stay investigations. Require passing role/payment regression tests and review before publishing changes with financial or authorization impact.
5. **Close only after release verification.** Link incident → regression → PR → server/OTA/native release. Re-run the failed scenario after publication, verify the new release receives telemetry, then observe sufficient relevant traffic without recurrence. Start with a 24-hour observation window; extend it for low-traffic paths. Zero events from a disconnected SDK is not evidence of a fix. Reopen on regression. Native fixes need a native release when applicable.
6. **Monitor the monitors.** Run a separately hosted health/egress probe about every minute, with repeated-failure thresholds. Track last successful Snyk scan per source SHA, last accepted telemetry event, failed notification jobs, and unacknowledged incidents. Use an explicitly tagged periodic synthetic canary and verify capture → rule match → actual destination receipt. Route canaries to a designated test destination so they do not page everyone. No canaries or destinations were activated during this audit.

Before activation, record the real incident owner/destination, obtain PostHog read access to verify project events/alerts, restore Snyk Code access, and verify notification receipt with that destination. These are the remaining external prerequisites; no alerting service can guarantee instant fixes without reproduction, validation, and release.

## Provider references

- [GitHub status-check semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions): a default `success()` check applies unless a status-check function is supplied.
- [Snyk CLI test outcomes](https://docs.snyk.io/developer-tools/snyk-cli/commands/test): distinguish clean, findings, execution failure, and no supported projects. Preserve structured scan results as well as exit status; the observed Forbidden output needs investigation regardless of the green wrapper.
- [PostHog API access](https://posthog.com/docs/api) and [alerts](https://posthog.com/docs/alerts): authenticated project verification and insight alerting are separate from installing the capture SDK.
- [Sentry alert actions](https://docs.sentry.io/api/monitors/fetch-an-alert/): configured actions/rule execution do not independently establish inbox receipt.
