# Minor-league schedule ingestion — bounded plan and access gap

Prepared September 5, 2026. This is a plan, not implemented ingestion or a launch approval. The provider exploration made no product-code changes, production queries/writes, provider enrollment, scraping or ingestion. See the [PDF status ledger](notes-remediation.md) for the remaining coverage requirement.

## Finding and access blocker

MLB's first-party StatsAPI is a technical candidate for affiliated minor baseball. Its current sports endpoint lists Triple-A (11), Double-A (12), High-A (13), Single-A (14), and Rookie (16). These match five existing catalog slugs. This endpoint establishes provider categories, not current fixture availability, venue completeness, a service guarantee, or application licensing. [Official sports endpoint](https://statsapi.mlb.com/api/v1/sports).

The JSON response links MLBAM's first-party policy: individual, non-commercial, non-bulk use is permitted; other use requires prior written authorization, and commercial uses remain limited to that authorization. Public/no-key access is therefore insufficient evidence that VarsityHub may import and redistribute schedules commercially. No applicable VarsityHub authorization or API-specific exception was supplied or found. Enabling this source requires evidence of authorization covering the intended schedule/venue use, caching/redistribution and request volume. No message to MLBAM was sent. [Response-linked usage policy](https://gdx.mlb.com/components/copyright.txt).

The [official API documentation](https://docs.statsapi.mlb.com/) yielded no readable documentation in the research browser. A schedule URL could not be opened by that browser's safety layer; this is not evidence of an upstream failure or current fixture counts. Provider SLA, request quotas and an approved contact/enrollment flow remain unverified.

The release owner's separate September 5 read-only production preflight reports 15 minor catalog entries and zero current events, versus ATP 2, WTA 3, and four NCAA sports with 1,008 events. This exploration did not rerun that production query. A new baseball adapter would not complete hockey/basketball/soccer minor-league coverage; the other ten catalog rows remain separate provider gaps. Arizona Fall League needs an independently verified league mapping, not the generic winter/minors category guessed from its name.

## Existing implementation and useful seams

- `server/prisma/schema.prisma`: Event already has unique nullable `pro_external_ref`, nullable `sports_league_id`, nullable pro-team IDs, provider-owned schedule/location fields, and independent posts/postingUnlocks. SportsLeague, SportsSeason and SportsIngestRun are already migrated models. SportsLeague is external metadata, never Team/Organization ownership.
- `server/src/lib/proSchedule/types.ts`, adapters, compositeAdapter, ingest and resolveFixture are currently TypeScript-coupled to the fixed Prisma ProLeague enum; ProviderTeam/ProTeam also require that enum. Simply selecting a minor catalog row does not make the current adapter capable of ingesting it.
- `resolveFixture.ts` provides the important venue/title checks, neutral-site no-home-fallback rule, cancellations without row deletion, and conservative event fields. `ingest.ts` batches existing refs, preserves banner/description/posts/grants, and has dry-run reporting. Reuse these semantics and a single shared writer.
- `server/src/jobs/scheduler.ts` runs the existing rolling job at 08:00 UTC via the shared scheduler; `pro-schedule-rolling.ts` already iterates adapter leagues independently and uses existing apply/provider gates. Scheduler provides Redis/BullMQ and Sentry integration. SportsIngestRun exists but this writer currently does not populate it.
- `eventCardSerializer.ts` already prefers SportsLeague sport/level metadata and passes live/upload access. Map's new Minor filter consumes it; no new coach ownership or native app surface is necessary.
- `server/scripts/mlb/sync-mlb-schedule.ts` is a legacy parallel importer using title plus a 12-hour window and deliberately merging doubleheaders. Do not extend/run it for this work; it violates the stable fixture identity needed here.

## Smallest implementation after access is resolved

1. Start with Triple-A only. Record an explicit provider/category mapping (`mlb_statsapi`, sportId 11 -> `milb_triple_a`) in existing SportsLeague metadata. Keep AA/High-A/Single-A/Rookie opt-in until their fixtures and venues are individually checked. No enum migration and no new Team/Organization/ProTeam rows for minors.
2. Generalize the normalized adapter boundary to catalog league slug plus optional legacy ProLeague mapping. Preserve existing adapters unchanged in behavior. Extract common title/time/coordinate validation and resolved Event writes once; existing pro-team resolver and a catalog fixture adapter both feed that same writer. Generic fixtures carry verified home/away display names and venue data, with null legacy team foreign keys. Fail closed on unrecognized catalog slug/provider category.
3. Add one StatsAPI adapter using the approved endpoint and request limits, `runWithBreaker`, timeout, bounded date chunks, schema validation, and a stable external ref such as `mlb_statsapi:game:<gamePk>`. Never derive identity from date/title; doubleheaders must remain distinct, while postponements/relocations retain their page, posts and grants. Explicitly validate UTC start vs local venue timezone, TBD times, status transitions and duplicate game IDs.
4. Obtain per-fixture venue coordinates/timezone from authorized provider data where present; use the existing venue/geocode mechanism only when needed and authorized. Missing/invalid coordinates, unresolved venue, or neutral-site ambiguity must produce a counted quarantine failure, never guessed coordinates or public unpostable pages. No team logos/media required for initial coverage.
5. Attach the adapter to the existing composite and rolling job behind explicit disabled-by-default source configuration. Use the existing configured horizon with a bounded correction lookback for recent games; validate lookback before launch. Log per-league fetched/created/updated/skipped/failure counts; on apply, record SportsIngestRun and Sentry failures/staleness. Dry run remains no event writes and emits a reviewable report. Do not report a provider failure as zero-event success.
6. Verify with synthetic fixtures and the guarded local audit DB: malformed rows, missing coordinates, neutral-site relocation, two same-day doubleheader games, unchanged replay causes no writes, moved/cancelled fixture keeps ID/posts/unlocks, unknown league rejection, failed fetch leaves prior data, and actual discovery -> Minor filter -> event detail -> unchanged grant/post authorization. Run one authorized live dry-run with actual counts/venue failures, then a bounded reviewed apply. Reconcile unique refs and map visibility before widening coverage.

## Release and reversibility

Expected schema migration: none for this bounded plan. New provider credentials/permission and actual source readiness are external dependencies, not completed work. Existing future-only rolling behavior needs a tested bounded lookback decision rather than an assumed change. Quarantine is currently reported failure metadata, not a persistent per-fixture queue; add no parallel queue.

Disabling the adapter stops writes without deleting existing event pages or their posts/grants. If imported rows require removal from discovery, mark only the exact new provider-reference set cancelled/inactive with a reviewed reconciliation; do not delete user content. Production readiness requires actual event data and successful ingest evidence; catalog entries and UI filters alone do not close the PDF coverage gap.
