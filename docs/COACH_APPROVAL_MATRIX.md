# Coach Approval Matrix — snapshot @ 39e70934 (branch: main)

## State-Defining Fields

The following fields on `User` and `User.preferences` define each row. All fields are read from the live database record by `requireOnboarded` on every guarded request; only `GET /auth/me` is cached (Redis, 60 s TTL), and every mutation that changes coach-gating calls `invalidateMeCacheForUser` immediately.

| Row | User columns | `preferences` keys |
|-----|-------------|-------------------|
| 1 — fan | `approval_status=APPROVED` (Prisma default), `paid_by_owner=false` | `role` absent or `role='fan'`, `onboarding_completed=true` |
| 2 — coach PENDING | `approval_status=PENDING`, `paid_by_owner=false`, `rejected_at=null` | `role='coach'`, `onboarding_completed=false`, `join_request_pending=true` (if org joined) |
| 3 — coach APPROVED no agreement | `approval_status=APPROVED`, `paid_by_owner=true` (or false if self-signup path) | `role='coach'`, `onboarding_completed=true`, `coach_agreement_accepted_at` absent/null |
| 4 — coach APPROVED agreement outdated | `approval_status=APPROVED` | `role='coach'`, `coach_agreement_accepted_at` present, `coach_agreement_version < REQUIRED_COACH_AGREEMENT_VERSION` (env var, default 1) |
| 5 — coach APPROVED + agreement + rookie | `approval_status=APPROVED`, `paid_by_owner=true\|false` | `role='coach'`, `coach_agreement_accepted_at` present, `coach_agreement_version >= required`, `plan='rookie'`, `payment_pending` absent/false |
| 6 — coach APPROVED + agreement + paid tier + payment_pending | `approval_status=APPROVED`, `paid_by_owner=false` | `role='coach'`, `plan='veteran'\|'legend'` or `pending_plan='veteran'\|'legend'`, `payment_pending=true`, `payment_approved=true` or `join_request_pending=false` |
| 7 — coach APPROVED + paid_by_owner | `approval_status=APPROVED`, `paid_by_owner=true` | `role='coach'`, `coach_agreement_accepted_at` present, any `plan` value |
| 8 — coach REJECTED within 48 h cooldown | `approval_status=REJECTED`, `rejected_at` within 48 h, `paid_by_owner=false` | `role='coach'`, `join_request_pending=false` |
| 9 — coach REJECTED cooldown expired | `approval_status=REJECTED`, `rejected_at` older than 48 h (or null → backfilled) | `role='coach'`, `join_request_pending=false` |
| 10 — coach APPROVED + org not admin_approved | `approval_status=APPROVED`, `paid_by_owner=true` | `role='coach'`, `organization_id` set, `coach_agreement_accepted_at` present; org row has `admin_approved=false` |

## Approval Path Distinction

**Platform admin approval** (`POST /admin/coaches/:id/approve`, `server/src/routes/admin.ts:178`, delegated to `server/src/lib/approvalService.ts:323`) — sets `approval_status=APPROVED` and `paid_by_owner=true` at the _platform_ level. Requires `isEmailAdmin` membership. Also calls `approveCoach` from `lib/approvalService.ts`.

**Organization owner approval** (`POST /organizations/:id/coaches/:userId/approve`, `server/src/routes/organizations.ts:2201`, and the join-request variant `POST /organizations/join-requests/:requestId/approve`, `server/src/routes/organizations.ts:1582`) — an org owner/manager approves a coach's membership in their specific org. Also sets `approval_status=APPROVED` and `paid_by_owner=true` and requires the org to already be `admin_approved` before the action can proceed (`organizations.ts:2274`).

Both paths converge on the same User row fields and both call `invalidateMeCacheForUser`. The join-request path in `organizations.ts:1670` uses `buildApprovedCoachPreferences`, the admin path uses `buildCoachApprovedPreferences` in `approvalService.ts:95` — functionally equivalent output.

## Discrepancies

**DISC-1 — `APPROVAL_REQUIRED` code collision (Severity: LOW / Cosmetic)**
`requireOnboarded.ts:145` returns `code: 'APPROVAL_REQUIRED'` for both "coach is PENDING" (state 2, line 129) and "coach APPROVED but org not admin_approved" (state 10, line 145). A client consuming the error code cannot distinguish "I need admin approval" from "my org needs admin approval". The `error` string differs but no structured field separates them. The client currently shows these states through redirect logic that only inspects `approval_status`, so the collision is invisible in the happy path but would confuse any future error-handling code or third-party API consumer.

**DISC-2 — Agreement version check absent on client (Severity: MEDIUM)**
`useRequireCoach.ts:43` checks `approvalStatus === 'APPROVED' && !prefs?.coach_agreement_accepted_at` and redirects to the agreement screen. It does not check `coach_agreement_version`. `AuthProvider.tsx:830-833` has the same blind spot. If `REQUIRED_COACH_AGREEMENT_VERSION` is bumped to force re-acceptance, `requireOnboarded.ts:171-179` blocks all guarded API calls with `COACH_AGREEMENT_OUTDATED`, but the client does not redirect the user to the agreement screen — the user sees a spinner or blank screen on coach tabs rather than being guided to re-accept. The client only enters the redirect path on the first acceptance (null `accepted_at`).

**DISC-3 — Org `admin_approved` not checked on client (Severity: LOW)**
`useRequireCoach.ts` and `AuthProvider.tsx` both consider `approval_status=APPROVED` as full clearance for client navigation. State 10 coaches will see coach tabs rendered and usable in the UI until any server call is made, at which point they receive `403 APPROVAL_REQUIRED`. There is no proactive client redirect to an "org pending" screen for this state. The `app/onboarding/league-pending-approval.tsx` screen exists but is only shown when `preferences.join_request_pending=true` — an already-APPROVED coach whose org lost approval (or whose org was never approved through an alternative path) lands in a broken state with no client guidance.

**DISC-4 — `null rejected_at` backfill starts cooldown from "now" (Severity: LOW / By design but undocumented)**
`auth.ts:1388-1396` and `auth.ts:1508-1515`: a legacy REJECTED user with no `rejected_at` has the timestamp backfilled to `new Date()` at call time, effectively starting the 48 h cooldown from the moment they first attempt to reapply, not from when they were originally rejected. This is documented in code comments as intentional but is not surfaced to the user — the `retry_after_hours` they receive reflects "48 hours from right now" with no explanation of why they were apparently rejected "just now."

**DISC-5 — `canAccessCoachTools` does not check `coach_agreement_version` (matches DISC-2)**
`hooks/useRequireCoach.ts:28-32` computes `canAccessCoachTools = isApprovedCoach && !!prefs.coach_agreement_accepted_at`. A coach with an outdated version (`coach_agreement_version < REQUIRED`) passes `canAccessCoachTools=true` and all coach screens render. Server rejects their calls with `COACH_AGREEMENT_OUTDATED` but client shows no redirect — screens appear functional until the first guarded API call fails.
