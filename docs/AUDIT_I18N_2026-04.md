# Audit: I18N Assumptions 2026-04

This audit did not find a current production bug. It found explicit US-only assumptions that are acceptable today and become bugs only if VarsityHub launches outside the US or supports non-USD billing.

## Current assumption

- Market: US-only
- Currency: USD-only
- Locale formatting: `en-US` is intentional in billing-adjacent paths

## Code locations

- [payments.ts](/Users/varsityhub/Desktop/CODE/VarsityHubMobile/server/src/routes/payments.ts)
  - `formatUsd()`
  - Stripe calls with `currency: 'usd'`
  - email date formatting using `'en-US'`
- [ad-calendar.tsx](/Users/varsityhub/Desktop/CODE/VarsityHubMobile/app/ad-calendar.tsx)
  - hardcoded dollar-sign rendering and `toFixed(2)` display formatting
- Apple IAP display paths
  - Apple-native `displayPrice` is correct
  - surrounding UI should not re-wrap that string with `$` or other USD-only assumptions

## Why this is not a bug today

- Stripe account and payment flows are configured for USD
- product scope is US users
- current pricing UI matches that scope

## What becomes a bug later

- any launch in a non-USD market
- country-specific tax-inclusive price display
- locale-aware date/currency rendering in billing emails or ads UI

## Future conversion plan

1. Centralize money formatting in a shared formatter instead of inline `$${value.toFixed(2)}`.
2. Treat currency as data from the server, not a UI constant.
3. Pass locale/currency into all billing emails and receipt formatting.
4. Preserve Apple `displayPrice` verbatim on client surfaces.

## Status

No code change required for `1.0.1`.
