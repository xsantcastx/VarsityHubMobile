## 1. Inline closures defeat `PostCard` memoization — **High**

`components/PostCard.tsx:850` correctly wraps the component in `React.memo`, and
the feed's `renderFeedItem` is wrapped in `useCallback` (`app/feed.tsx:1384`).
But inside `renderFeedItem`, every `PostCard` is handed freshly-created arrow
functions each render (`app/feed.tsx` ~1616–1640):

```tsx
<PostCard
  post={post}
  onPress={() => router.push(`/post-detail?id=...&postIds=${followedPosts.map(...)}...`)}
  onDeleted={postId => setFollowedPosts(prev => prev.filter(...))}
  onUpdated={updated => setFollowedPosts(prev => prev.map(...))}
/>
```

Because `onPress`/`onDeleted`/`onUpdated` are new references on every feed
render, `React.memo`'s shallow prop compare always fails, so **every visible
`PostCard` re-renders** whenever any feed-level state changes (unread count,
notification poll, refresh tick, etc.). This is the single highest-value fix:
the feed is the app's hottest screen and `PostCard` is a heavy component
(media, avatars, action bar).

Fix: hoist stable per-item handlers — pass the `post`/`id` into memoized
callbacks (`useCallback` keyed on nothing, receiving the id as an argument), or
move navigation/mutation handling inside `PostCard` so the closures don't cross
the memo boundary.

Note: the `followedPosts.map(...)` inside `onPress` only runs on tap (not per
render), so it is not itself a render-cost issue — but it does allocate the
closure that breaks memo.

## 2. `messages` renderItem callbacks not memoized — **Medium**

`app/messages.tsx:347` (`renderConversation`) and `app/messages.tsx:416`
(`renderUserSearchItem`) are declared as plain `const` inside the component
body, so a new function is created on every render and passed to
`<FlatList renderItem=...>` (`:628`, `:732`, `:740`). This forces FlatList to
treat the render function as changed each cycle.

Contrast with the correct pattern already used elsewhere in the codebase —
`app/favorites.tsx:186` and `app/team-join-requests.tsx:134` both wrap
`renderItem` in `useCallback`. Apply the same here.

## 3. Inline-arrow renderItem + non-memoized item bodies across list screens — **Medium**

Many screens define `renderItem={({ item }) => (...)}` inline in JSX, which
allocates a new render function every parent render and inlines the item markup
(so no item component can be memoized). Confirmed occurrences:

- `app/game-photos.tsx:22`, `app/team-invites.tsx:103`, `app/blocked-users.tsx:146`
- `app/admin-teams.tsx:191`, `app/admin-users.tsx:142`, `app/admin-transactions.tsx:164`
- `app/admin-messages.tsx:74`, `app/organization-invites.tsx:131`, `app/game-reviews.tsx:20`
- `app/game-highlights.tsx:21`, `app/manage-users.tsx:226`, `app/public-event.tsx:321`
- `app/profile.tsx:1410,1535,1661`, `app/team-page.tsx:997,1097,1198,1299`
- `app/post-detail.tsx:1857`, and the notifications list in `app/feed.tsx:2281`

Only 3 of 66 files under `components/` use `React.memo`, so the list-row markup
in these screens is not extractable-and-memoized today. Impact is Medium
(most of these are short admin/utility lists), but `profile.tsx` and
`team-page.tsx` render multi-tab post/media grids and are worth extracting into
memoized row components with `useCallback` render functions.

Good news: **every** FlatList audited already supplies a `keyExtractor`, and the
main feed already sets `maxToRenderPerBatch` / `windowSize` /
`removeClippedSubviews` (`app/feed.tsx:2278–2280`) — so virtualization tuning is
not a gap; only the per-item memoization is.

## 4. Inline computed style objects in list rows — **Low**

`renderFeedItem` builds inline `style={{ ... }}` objects with computed
(theme-dependent) values on each render, e.g. the `seed_banner` block
(`app/feed.tsx:1395–1420`) and the notification `listRow` inline style array
(`app/feed.tsx:2287–2291`). These allocate fresh objects/arrays every render.
Individually cheap (single elements or small lists), but the pattern is
pervasive; prefer `StyleSheet.create` + a memoized theme-color lookup so the
style identity is stable.

## 5. Geocode backfill loops run sequential `await` per row — **Low**

Not a per-request N+1 — these are one-time startup backfills, each bounded by
`take: 1000`, and explicitly documented as such in-code:

- `server/src/routes/events.ts:257` `runEventsStartupBackfill` — loop at `:268`,
  `geocodeLocation` + `event.update` awaited per row.
- `server/src/routes/games.ts:695` — loop at `:705`, `geocodeLocation` +
  `game.update` + `event.updateMany` awaited per row.
- `server/src/routes/ads.ts:173/534/1110` — `getZipCoordinatesWithFallback`
  awaited inside loops (ad ZIP resolution).

They run at boot (or on bounded input), so user-facing latency is nil. If backfill
duration ever matters, batch with a bounded `Promise.all` (respecting the geocoder
rate limit). Left Low.

**No true per-request N+1 was found.** The response-building routes that load a
list and then need per-item data correctly use IN-clause batching / `groupBy`
instead of per-row queries — e.g. `server/src/routes/users.ts:634` (`findMany`
`where id: { in: [...] }`), `:642` (`comment.groupBy`), and
`server/src/routes/highlights.ts:164` (single `findMany take: 300`). This matches
the repo's `unbounded-queries` test gate.

## 6. Contexts are well-split and memoized — **Positive, no action**

The routine flags `AuthContext` / `PostCacheContext` as re-render risks; both are
handled correctly here:

- `context/AuthProvider.tsx:1310` memoizes the provider `value` with `useMemo`
  and a complete dependency array; every exposed method is a `useCallback`
  (`checkAuth`, `signOut`, `registerPushToken`, onboarding markers, etc.). The
  value identity changes only when real state changes.
- `context/PostCacheContext.tsx:87` memoizes its `value`; all mutators are
  `useCallback`-stable over a stable `Map` instance (`:45`). By design the Map is
  mutated in place and does **not** trigger consumer re-renders (it's a cross-screen
  cache, not reactive state) — consistent with CLAUDE.md's "PostCacheContext is
  cross-screen post sharing, NOT a fetch cache."

No large, frequently-changing context object was found. No action needed.

## 7. Image loading is already optimized — **Positive, no action**

`components/PostCard.tsx` (the feed's image-heavy component) uses `expo-image`
(`:9`) with `contentFit="cover"`, `cachePolicy="memory-disk"`, `recyclingKey`,
`transition`, and server-side resizing via `optimizeImageUrl(url, 80|600)`
(`:243`, `:307`, `:332`). This is the correct pattern for a virtualized list.
The remaining plain `react-native` `<Image>` hits are static local assets (e.g.
the logo at `app/feed.tsx:2133`), which need no remote caching/sizing. No action.

## Recommended order of work

1. **Finding 1 (High)** — stabilize the `PostCard` handler closures in the feed;
   biggest real-world win, hottest screen.
2. **Finding 2 (Medium)** — wrap the two `messages` render functions in
   `useCallback` (one-line fix each, pattern already in the codebase).
3. **Finding 3 (Medium)** — extract + memoize row components for `profile.tsx`
   and `team-page.tsx` first (heaviest lists), then the admin screens as cleanup.
4. **Finding 4 (Low)** — move inline computed styles to `StyleSheet` + memoized
   theme lookups opportunistically while touching the above.
